## ARCHITECTURE INTUITION

Treat transformer inference as two classes of work:

- Data-dependent: token N before N+1, router output before exact expert fetch, KV page commit before
  later attention.
- Data-independent: weight staging, KV page prefetch, tensor layout validation, inactive request
  admission, batch packing.

Fuse the data-independent work heavily: row-column bundled reads, cuBLASLt epilogues, fused
RMSNorm/RoPE/SwiGLU where useful, FlashAttention where applicable, and SGMV for multi-user
LoRA/MoE batches.

Decode is memory-bound; prefill is compute-bound. Continuous batching must mix decode steps and
chunked prefill to keep the GPU fed. Speculative decoding and Eagle 3 are throughput tools only
after the measured first-token path exists.

VRAM and RAM are scratchpads. NVMe is the durable model/KV backing tier. Placement is an
optimization problem, not an allocator accident. Multi-user is the normal case: shared base weights,
per-request KV/page tables, per-user adapters, iteration-level scheduling.

## VISION LOCK

Blok is not a conventional in-memory inference runtime with an emergency offload path. Blok is an
SSD-resident inference runtime. The model, prompt material, KV state, auxiliary checkpoints, layout
indexes, and benchmark artifacts live on NVMe by default. GPU VRAM and system RAM are bounded
scratchpads whose contents are justified only by the next scheduled operations.

The runtime wins by turning deterministic inference into a storage and compute schedule:

1. Compile the graph far enough ahead that every payload byte has a known source range, destination
   arena view, lifetime, consumer op, and release point.
2. Store tensors on SSD in the order the schedule wants to read them, not in the order the source
   checkpoint happened to ship them.
3. Use sparsity to avoid transferring inactive rows, experts, KV pages, adapters, and speculative
   branches.
4. Batch and bundle the bytes that remain into large contiguous reads that match NVMe behavior.
5. Fuse the compute that consumes those bytes so the GPU spends time on dense math, not launch
   overhead, host waits, and small memory-bound kernels.
6. Measure the path as storage-to-kernel-to-token, with no unreported payload `mmap`, page-cache
   fallback, implicit migration, or compatibility bounce path.

The core product claim is therefore precise: a model can be larger than memory because memory is not
the owner of the model. The scheduler owns the working set, the SSD owns durable bytes, and the GPU
owns the math.

## FUNDAMENTAL RESEARCH NOTES

These notes are implementation constraints, not background reading.

- NVIDIA GDS confirms the desired baseline shape: explicit transfers between storage and GPU memory
  avoid CPU bounce buffers, require direct/aligned behavior for the strongest path, and are most
  appropriate for coarse streaming transfers. GDS also has compatibility modes that may stage
  through CPU memory, so Blok reports direct, staged, and fallback paths separately and does not
  count compatibility mode as a direct-path success.
  Reference: https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html
- uGDS is the preferred open path because it bypasses the kernel NVMe driver and filesystem, lets
  user space build NVMe commands, and uses `ugds_drv` for BAR mapping and GPU page pinning. This
  strengthens the rule that a uGDS device is a block-device ownership mode, not an ordinary mounted
  filesystem mode.
  Reference: https://github.com/ScaleX-IO/uGDS
- FlexGen proves that GPU, CPU, and disk placement should be modeled as an optimization problem
  rather than hidden behind opportunistic offload. Its linear-programming placement search and
  high-throughput batching are directly aligned with Blok's scheduler contract, even though Blok's
  first path must be lower level and more explicit about direct I/O and GPU residency.
  Reference: https://arxiv.org/abs/2303.06865
- LLM in a flash proves that flash-aware inference has two different levers: reduce transferred
  bytes with activation/sparsity reuse, and make remaining reads larger and more contiguous with
  row-column bundling. Blok should treat small random tensor reads as a layout failure unless a
  measured sparse path beats the bundled read path.
  Reference: https://arxiv.org/abs/2312.11514
- FlashAttention proves the local version of the same thesis inside the GPU: exact attention can be
  faster when the algorithm is designed around memory hierarchy and tiling. Blok should apply the
  same discipline across SSD, PCIe, HBM, shared memory, and registers.
  Reference: https://arxiv.org/abs/2205.14135
- PagedAttention proves that KV cache management determines serving throughput and that block-level
  KV allocation enables dynamic batching, sharing, and lower fragmentation. Blok should keep the
  paged-KV abstraction but make every page spill/prefetch decision explicit in the SSD-backed graph.
  Reference: https://arxiv.org/abs/2309.06180
- vAttention is the warning case: preserving contiguous virtual-memory views can simplify attention
  kernel integration, but demand-paging-style behavior conflicts with Blok's no-hidden-payload-path
  invariant unless every migration is observable and schedulable. Use CUDA virtual memory only when
  it preserves explicit placement reports.
  Reference: https://arxiv.org/abs/2405.04437
- Punica/SGMV shows that multi-tenant adapter work should be grouped into specialized kernels
  rather than handled as many small GEMMs. The same principle applies to MoE expert fragments,
  LoRA/adapters, and per-user sparse deltas.
  Reference: https://arxiv.org/abs/2310.18547
- EAGLE-3/speculative decoding belongs after the first measured path. It can improve token
  throughput only if accepted-token gains exceed auxiliary-model, KV, scheduling, and rollback
  costs in Blok's SSD-backed execution report.
  Reference: https://arxiv.org/abs/2503.01840

## DEEP QUESTIONS TO RESOLVE

These are blocking design questions for the next architecture pass. Answers should be written back
into this file or into the owning module docs before implementation assumes them.

1. Product target: is Blok optimizing first for one local interactive user, a local batch queue, or a
   multi-user server? Continuous batching, KV eviction, first-token latency, and speculative
   decoding policy differ sharply across those targets.
2. Latency target: what first-token latency and steady token/s are acceptable for the first huge MoE
   demo on the RTX 5060 Ti with one Samsung NVMe? If the target is "works at all," the scheduler can
   favor proof and observability; if the target is interactive, D1-D3 must include overlap earlier.
3. Model target: which exact first forcing checkpoint should define the manifest and layout work:
   DeepSeek R1 GGUF, a Hugging Face safetensors checkpoint, or a smaller architecturally similar
   MLA/MoE model used as the correctness ladder?
4. Accuracy contract: which quantized formats are acceptable for first success? The current plan
   prefers bf16 compute and fuses dequant into matmul, but huge SSD-resident models may require a
   specific weight quantization and KV quantization policy.
5. SSD ownership: will there be a dedicated non-root NVMe for uGDS, or must the first phase work
   entirely from the mounted root NVMe through GDS and `O_DIRECT` fallback? uGDS success requires a
   device that can leave the kernel `nvme` path.
6. Data permanence: should prompts, KV cache, and optimizer checkpoints all persist across process
   restarts, or is "stored on SSD" limited to model bytes plus runtime spill files with explicit
   cleanup?
7. KV policy: should the first long-context path use exact paged KV with spill/prefetch only, or is
   KV compression/pruning acceptable once reports can show quality and speed impact?
8. Sparsity policy: for MoE and activation sparsity, should the runtime prioritize guaranteed exact
   model semantics first, or allow approximate sparse activation reuse from the beginning when the
   source paper supports it?
9. Scheduler math: should placement initially be a simple deterministic heuristic with logged
   constraints, or should S0-S2 already reserve a linear-programming interface compatible with
   FlexGen-style optimization?
10. Layout authority: is Blok allowed to rewrite/repack model files into its own physical tensor
    layout, or must it preserve source checkpoint files and build sidecar indexes only?
11. Filesystem boundary: should model storage be ordinary files with `O_DIRECT`/cuFile until uGDS,
    or should Blok define a raw-block layout for the dedicated model NVMe early?
12. Safety boundary: what destructive operations may the tooling ever perform on NVMe devices?
    Formatting, rebinding, firmware updates, and benchmark writes need explicit operator gates.
13. CPU role: should CPU cores be used only for scheduling and I/O polling, or should CPU compute
    also handle tokenization, sampling, router preprocessing, layout planning, and fallback kernels?
14. Kernel strategy: should first kernels rely on cuBLASLt and FlashAttention-compatible libraries
    wherever possible, with custom CUDA only for missing glue, or should Blok own custom kernels
    earlier to control fusion and scheduling?
15. Observability format: should reports be JSON Lines for streaming remote comparison, one JSON
    artifact per run, or both?
16. Failure policy: when a direct path silently falls back to staging, should generation abort by
    default, or continue only under an explicit `--allow-staged-io` flag?
17. Development ladder: what is the smallest model and tensor fixture that still exercises the same
    manifest, layout, arena, I/O, CUDA, and graph path as the huge MoE target?
18. External compatibility: is the goal a standalone CLI first, an OpenAI-compatible server later,
    or an embeddable runtime API?
19. Speculation policy: is EAGLE-3 required for the product vision, or is it an optional throughput
    layer after deterministic SSD execution is proven?
20. Success definition: after first token works, is the next milestone lower latency, longer context,
    larger model, more users, or cleaner hardware portability?

## PROVISIONAL ANSWERS UNTIL OVERRIDDEN

Use these defaults to keep implementation moving. Replace them with user-confirmed decisions as
soon as the deep questions are answered.

- Product target: local CLI first, multi-user scheduler architecture from day one, server API later.
- Latency target: first token correctness and measurement before interactivity; overlap is required
  by D2 and mandatory by D3.
- Model ladder: tiny deterministic tensor fixture, then small dense model, then small MoE/MLA model,
  then the huge forcing checkpoint.
- Storage mode: ordinary files with explicit `O_DIRECT`/GDS first; uGDS requires a dedicated
  non-root NVMe before it can be a release gate.
- Layout mode: build a Blok sidecar layout first; allow full repack only after the sidecar path
  proves which source-checkpoint order is inefficient.
- Scheduler math: start with a deterministic heuristic whose inputs and constraints match a future
  linear-programming model. Do not introduce an LP solver until reports show heuristic placement is
  the bottleneck or the model no longer fits the simple policy.
- Sparsity mode: exact model semantics first. Use sparsity for MoE expert selection, inactive KV
  movement, adapter selection, and storage layout before approximate activation reuse.
- Kernel mode: cuBLASLt, CUDA graphs, CUDA events, and known attention kernels first; custom CUDA
  kernels only where fusion, sparse grouping, or direct-path integration requires ownership.
- Failure mode: direct-path violation aborts by default. Staged I/O requires an explicit opt-in flag
  and is reported as a different backend.
- Report mode: emit one JSON artifact per run plus optional JSON Lines for long-running remote
  benches.

## COMPUTE-BOUND ACCEPTANCE RULES

"Massively compute bound" is a measurable requirement, not a slogan. A milestone does not claim GPU
saturation unless its report separates and explains:

- payload bytes scheduled from SSD, bytes actually moved, and direct/staged/fallback backend;
- GPU kernel time, transfer time, host submission time, and dependency stall time;
- achieved TFLOPs or effective bandwidth for each compute kernel;
- overlap ratio between transfer N+1 and compute N;
- launch count per token and fused-op count per token;
- arithmetic intensity estimate for each scheduled operation;
- reason for every unfused operation left in the hot path.

D1 may be underutilized because it proves the first byte-to-kernel path. D2 must show which part of
one layer is storage-bound, launch-bound, memory-bound, or compute-bound. D3 must either make the
forward step compute-bound or produce a report that names the exact missing fusion, layout,
prefetch, batching, or kernel work needed to get there.

## SCHEDULER CONTRACT

Every scheduled operation is represented by a typed descriptor before payload movement starts:

- operation id, layer id, request ids, and token range;
- source tensor ranges or KV page ranges with offset, size, alignment, dtype, and checksum policy;
- destination arena view with memory tier, offset, size, alignment, stream, and lifetime;
- compute consumer with kernel/library name, shape, dtype, expected FLOPs, and fusion epilogue;
- dependency edges for router output, KV commit, transfer completion, and compute completion;
- release action for SSD scratch, host pinned memory, device memory, and KV page table entries;
- report fields that prove whether the operation followed the planned path.

No hot-path code may discover a new payload range by filename lookup, metadata parsing, allocator
growth, page fault, or implicit framework behavior. Discovery belongs to manifest/layout/graph
construction; execution consumes descriptors.

## SPARSITY AND LAYOUT STRATEGY

Sparsity is useful only when it reduces total wall time after accounting for read size, transfer
overhead, kernel shape, and batching loss. The layout planner therefore evaluates sparse choices in
this order:

1. Deterministic structural sparsity: MoE router-selected experts, adapter selection, inactive
   request branches, and unused KV pages.
2. Storage-contiguous sparse groups: row-column bundles and expert groups that can be fetched as
   large ranges.
3. Runtime sparse kernels: SGMV-style grouped operations for many small per-user or per-expert
   matrices.
4. Approximate activation reuse or pruning: only after exact execution reports exist and quality
   evaluation is wired.

The planner should prefer reading a larger contiguous range over many tiny random ranges unless a
report proves the smaller transfer wins end to end.

## SSD OWNERSHIP MODEL

Blok recognizes four SSD roles:

- `root`: mounted OS/development disk. Allowed for metadata, sidecar files, GDS reads where
  supported, and `O_DIRECT` fallback tests. Never rebound to uGDS.
- `model`: mounted or raw model storage. Allowed to hold source checkpoints, Blok layouts, prompt
  artifacts, and KV spill files.
- `benchmark`: disposable device or namespace. Allowed for destructive bandwidth, write, erase, and
  rebind tests after explicit operator confirmation.
- `ugds`: dedicated device owned by `ugds_drv`. Not a mounted filesystem while active; all reads and
  writes happen through the uGDS API contract.

Hardware probes must label each observed NVMe with one of these roles or `unknown`, and write tests
must refuse `root` unless they are explicitly marked nondestructive.

## DATAFLOW

1. `manifest` reads metadata only and builds a complete tensor map.
2. `layout` validates or writes physical ranges optimized for sequential NVMe reads.
3. `hardware` measures the actual machine and exports bandwidth/topology constraints.
4. `graph` lowers the model into layer/expert/KV operations with explicit dependencies.
5. `arena` reserves bounded scratch capacity and returns offset views.
6. `io` stages required tensor ranges into arena views.
7. `cuda` waits on transfer events, launches fused compute, records completion events.
8. `decode` schedules users at token granularity and feeds the next graph iteration.
9. `observe` reports bytes moved, ops launched, bandwidth, overlap, and failure point.

## MODEL SUPPORT

- Architecture families: dense, GQA, MoE, MLA, hybrid token mixers.
- MLA rule: cache latent content and decoupled RoPE vector separately; never apply RoPE to latent
  cache.
- MoE rule: router result is data-dependent; expert storage layout and prefetch candidates are
  compiled ahead.
- Quant rule: weight quantization is per tensor; dequant must be fused with the consuming matmul
  path when performance matters.
- Format rule: support GGUF and Hugging Face-style metadata through the same `Manifest`; runtime
  consumes `Manifest`, not source format quirks.
- Auxiliary-model rule: Eagle 3 and scheduler/predictor models live under optimizer ownership, not
  target-model ownership, and must be measured as runtime overhead.

## HARDWARE RULES

- RTX 5060 Ti must probe as compute capability 12.0 / `sm_120` before enabling the Blackwell path;
  compile flags and kernel dispatch derive from the probe, not from the product string.
- The `sm_120` path uses bf16 by default; f16 is rejected unless explicitly justified by a kernel
  contract.
- Thread pinning derives from measured cache/NUMA topology. On the current 5950X, prefer separate
  L3 groups for CUDA submission and I/O polling; do not hard-code CPU numbers in config defaults.
- NVMe reads are aligned, large, and sequential where layout permits; small random reads are a
  failure mode.
- Preferred direct path is uGDS where device binding and kernel module state permit it.
- Compatibility direct path is NVIDIA GDS/cuFile.
- Fallback path uses `io_uring` plus `O_DIRECT` plus fixed aligned buffers; normal buffered reads
  are not allowed for tensor payload.
- GDS compatibility mode is not accepted as H2 success. The report must state whether bytes reached
  GPU memory through a direct path, compatibility staging, or fallback I/O.
- `stream.synchronize()` is not used in the hot overlap path; CUDA events express ordering.
- A mounted root disk is never rebound to uGDS. Root-mounted NVMe can be used for GDS/cuFile and
  `O_DIRECT` read tests that do not require block-device ownership changes.

## TESTS

- Unit tests: manifest validation, alignment, arena bounds, KV page tables, MLA RoPE separation.
- CPU tests: deterministic tiny graph, tokenizer roundtrip, scheduler admission/ejection.
- Linux ignored hardware tests: uGDS/GDS roundtrip, direct-I/O fallback, cuBLASLt bf16, CUDA graph
  launch, double-buffer overlap.
- End-to-end gate: first token on huge MoE with no payload `mmap`, no unbounded allocation, and
  complete report.
- Regression gate: static checks reject TODO, payload `mmap`, untyped magic sizes, hot-path
  allocation, and accidental f16 in `sm_120` runtime.

## MAC-TO-LINUX LOOP

- `just fmt-check` and `just check-local` run locally for portable code.
- `cargo xtask remote check --host <pc>` syncs repo to Linux and runs full feature checks.
- `cargo xtask remote bench --host <pc> --model <path>` runs hardware gates and first-token path.
- SSH runner owns build/test orchestration; the Linux PC owns production execution.
- Remote runs must return structured reports to the dev machine; do not rely on ad hoc terminal
  transcripts as the only artifact.

## ANTI-DRIFT

- Do not add a second runtime path when the current one can be edited.
- Do not add a crate to express architecture preference.
- Do not add a probe unless a current milestone lacks a required measurement.
- Do not read broad context when a targeted query can answer the question.
- Do not hide unsupported paths behind defaults; return typed capability errors.
- Do not optimize by belief; add the smallest measurement that proves the bottleneck.
- If code grows, first delete stale code, wrappers, duplicated enums, or unused reports.
- Do not let placeholder docs and executable modules describe the same ownership twice.
