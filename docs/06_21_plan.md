
  # BLOK GOLDEN IMPLEMENTATION PLAN

  ## TARGET

  blok generate --model <huge-moe-model> --prompt "Hi" --tokens 1 emits the first token on the Linux PC, with measured NVMe→VRAM bytes, kernel time, memory use, and no hidden payload mmap/cache path.

  ## MACHINE

  - Dev control plane: macOS repo editing + xtask remote.
  - Production target: Ubuntu bare metal, RTX 5060 Ti / sm_120, Ryzen 9900X, Samsung PCIe 5 NVMe.
  - First forcing model: DeepSeek R1 GGUF or equivalent giant MLA/MoE checkpoint; this is a stress target, not a format limitation.

  ## REFERENCES

  - GDS/O_DIRECT: https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html
  - CUDA graphs: https://docs.nvidia.com/cuda/cuda-programming-guide/index.html
  - FlexGen: https://arxiv.org/abs/2303.06865
  - LLM in a Flash: https://arxiv.org/abs/2312.11514
  - PagedAttention: https://dl.acm.org/doi/10.1145/3600006.3613165
  - Punica/SGMV: https://arxiv.org/pdf/2310.18547.pdf
  - uGDS: https://github.com/ScaleX-IO/uGDS

  ## NON-NEGOTIABLES

  - Professional diction, tight names, tight code, no duplicate paths, no placeholder plumbing.
  - One persistent plan; edit this plan, do not create plan variants.
  - One Rust crate blok plus xtask; split files only when a measured hardware boundary forces it.
  - Every added line must either drive hardware, describe the deterministic graph, enforce safety, or remove ambiguity.
  - Declared working set only: before touching bytes, code must know offset, size, alignment, destination arena, lifetime, and consumer op.
  - No payload mmap; metadata windows are capped and payload moves through explicit direct I/O or GDS.
  - Inference is deterministic: compile the data path up front, schedule movement before compute needs it, and measure every transfer.

  ## ARCHITECTURE INTUITION

  - Treat transformer inference as two classes of work:
      - Data-dependent: token N before N+1, router output before exact expert fetch, KV page commit before later attention.
      - Data-independent: weight staging, KV page prefetch, tensor layout validation, inactive request admission, batch packing.

  - Fuse the data-independent work heavily: row-column bundled reads, cuBLASLt epilogues, fused RMSNorm/RoPE/SwiGLU where useful, SGMV for multi-user LoRA/MoE batches.
  - Decode is memory-bound; prefill is compute-bound. Continuous batching must mix decode steps and chunked prefill to keep the GPU fed.
  - VRAM and RAM are scratchpads. NVMe is the durable model/KV backing tier. Placement is an optimization problem, not an allocator accident.
  - Multi-user is the normal case: shared base weights, per-request KV/page tables, per-user adapters, iteration-level scheduling.

  ## FILE PLAN

  Keep the implementation under one crate:

  - src/main.rs: CLI only; no runtime logic.
  - src/config.rs: typed constants, env parsing, no magic numbers.
  - src/hardware.rs: Linux hardware probes, PCIe/NVMe/GPU/CPU topology, capability errors.
  - src/manifest.rs: model tensor index, architecture metadata, quant/KV/layout rules.
  - src/layout.rs: install-time physical tensor layout, row-column MoE bundling, contiguous ranges.
  - src/arena.rs: pinned host/device arena views; no hot-path allocation.
  - src/io.rs: GDS first, io_uring/O_DIRECT fallback, aligned transfer descriptors.
  - src/cuda.rs: CUDA context, streams, events, cuBLASLt, CUDA graphs, feature-gated Linux only.
  - src/graph.rs: deterministic execution DAG, data dependencies, transfer/compute overlap.
  - src/kv.rs: paged KV, MLA latent + decoupled RoPE KV, optional quantized persistence.
  - src/kernels.rs: kernel registry and launch descriptors, not kernel policy.
  - src/decode.rs: continuous batching, chunked prefill, first-token/full-token loop.
  - src/observe.rs: counters, bandwidth, timing, RSS, page faults, structured reports.
  - xtask/src/main.rs: macOS→Linux SSH sync/check/bench runner.

  Delete or merge any module that becomes a passive wrapper.

  ## DATAFLOW

  1. manifest reads metadata only and builds a complete tensor map.
  2. layout validates or writes physical ranges optimized for sequential NVMe reads.
  3. hardware measures the actual machine and exports bandwidth/topology constraints.
  4. graph lowers the model into layer/expert/KV operations with explicit dependencies.
  5. arena reserves bounded scratch capacity and returns offset views.
  6. io stages required tensor ranges into arena views.
  7. cuda waits on transfer events, launches fused compute, records completion events.
  8. decode schedules users at token granularity and feeds the next graph iteration.
  9. observe reports bytes moved, ops launched, bandwidth, overlap, and failure point.

  ## MODEL SUPPORT

  - Architecture families: dense, GQA, MoE, MLA, hybrid token mixers.
  - MLA rule: cache latent content and decoupled RoPE vector separately; never apply RoPE to latent cache.
  - MoE rule: router result is data-dependent; expert storage layout and prefetch candidates are compiled ahead.
  - Quant rule: weight quantization is per tensor; dequant must be fused with the consuming matmul path when performance matters.
  - Format rule: support GGUF and Hugging Face-style metadata through the same Manifest; runtime consumes Manifest, not source format quirks.

  ## HARDWARE RULES

  - RTX 5060 Ti/sm_120 path uses bf16 by default; f16 use is rejected unless explicitly justified by a kernel contract.
  - CUDA submission thread pins to CCD0; I/O polling thread pins to CCD1 on Ryzen 9900X.
  - NVMe reads are aligned, large, and sequential where layout permits; small random reads are a failure mode.
  - GDS path uses registered CUDA buffers and CUDA-stream ordered I/O.
  - Fallback path uses io_uring + O_DIRECT + fixed aligned buffers; normal buffered reads are not allowed for tensor payload.
  - stream.synchronize() is not used in the hot overlap path; CUDA events express ordering.

  ## OBSERVABILITY

  Every milestone prints one compact report:

  - hardware: GPU, driver, CUDA, PCIe, NVMe, CPU topology.
  - memory: arena sizes, live views, RSS, page faults, pinned bytes.
  - I/O: offset, size, alignment, backend, elapsed, GB/s.
  - compute: kernel, dtype, shape, elapsed, achieved bandwidth/TFLOPs.
  - graph: dependency stalls, overlap ratio, bytes scheduled vs bytes moved.
  - decode: users, prefill chunks, decode steps, KV pages, token latency.

  ## TESTS

  - Unit tests: manifest validation, alignment, arena bounds, KV page tables, MLA RoPE separation.
  - CPU tests: deterministic tiny graph, tokenizer roundtrip, scheduler admission/ejection.
  - Linux ignored hardware tests: GDS roundtrip, GDS bandwidth, io_uring fallback, cuBLASLt bf16, CUDA graph launch, double-buffer overlap.
  - End-to-end gate: first token on huge MoE with no payload mmap, no unbounded allocation, and complete report.
  - Regression gate: grep/static checks reject TODO, payload mmap, untyped magic sizes, hot-path allocation, and accidental f16 in sm_120 runtime.

  ## MAC→LINUX LOOP

  - cargo fmt && cargo test runs locally on macOS for portable code.
  - cargo xtask remote check --host <pc> syncs repo to Linux and runs full feature checks.
  - cargo xtask remote bench --host <pc> --model <path> runs hardware gates and first-token path.
  - SSH runner owns build/test orchestration; the Linux PC owns production execution.

  ## ANTI-DRIFT

  - Do not add a second runtime path when the current one can be edited.
  - Do not add a crate to express architecture preference.
  - Do not add a probe unless a current milestone lacks a required measurement.
  - Do not read broad context when a targeted query can answer the question.
  - Do not hide unsupported paths behind defaults; return typed capability errors.
  - Do not optimize by belief; add the smallest measurement that proves the bottleneck.
  - If code grows, first delete stale code, wrappers, duplicated enums, or unused reports.
