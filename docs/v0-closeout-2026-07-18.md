# Blok Kimi K2.6 V0 closeout

Date: 2026-07-18

This document records the complete scope of the V0 closeout pass, every repository change made during the pass, the checks that were run, and the exact target-machine procedure that remains. It is intentionally candid: the repository is prepared for the first target run, but a successful CUDA build, uGDS execution, and Kimi answer have not been observed in this Mac development environment.

## V0 decision

V0 is deliberately Kimi K2.6-specific. Its goal is one correct, full, native forward/generation path using the pinned official Kimi checkpoint and direct NVMe-to-GPU reads on the target machine. General model support, concurrent requests, million-token generation, 50-trillion-parameter layouts, and peak-speed optimization are future work.

The target is:

- Ubuntu/Linux
- AMD Ryzen 9 5950X
- NVIDIA GeForce RTX 5060 Ti 16 GB, compute capability 12.0
- CUDA 12.8 or newer
- NVIDIA open kernel modules
- Samsung 990 EVO Plus 1 TB NVMe
- uGDS device `/dev/ugds_drv0`, unless overridden
- Kimi K2.6 revision `7eb5002f6aadc958aed6a9177b7ed26bb94011bb`

The V0 engineering priorities are correctness, a small native path, explicit contracts, and a target workflow that fails early when the machine or model does not match. No inline PTX was added in this pass. Adding architecture-specific assembly before the CUDA path compiles and produces reference-correct output on the target would make correctness harder to establish.

The relevant text-model contract is:

| Property | Value |
| --- | ---: |
| Layers | 61 |
| Hidden size | 7,168 |
| Attention heads | 64 |
| Query LoRA rank | 1,536 |
| KV LoRA rank | 512 |
| QK no-RoPE dimension | 128 |
| QK RoPE dimension | 64 |
| Value dimension | 128 |
| Dense intermediate size | 18,432 |
| MoE intermediate size | 2,048 |
| Shared experts | 1 |
| Routed experts | 384 |

The runtime only indexes `language_model.*` tensors. Vision and multimodal tensors in the checkpoint are intentionally excluded from this text-only V0.

## Defects found and resolved

| Defect | Resolution |
| --- | --- |
| Routed experts were discovered as `.weight`, while the checkpoint stores `.weight_packed`, `.weight_scale`, and `.weight_shape`. | The materializer, runtime-slot parser, contract checker, and CUDA lookup now use the packed checkpoint names. |
| Shared-expert matrix widths were treated as the dense 18,432 width. | Dense FFN width remains 18,432; shared and routed MoE widths are now 2,048. |
| Materialized metadata and Python runtime discovery used different paths. | Payload storage and metadata storage now have separate, consistent roots, and the runtime can resolve a manifest or its containing metadata directory. |
| Tokenizer readiness required `tokenizer.json`, which is absent from the pinned revision. | Materialization now consumes `tiktoken.model` and `tokenizer_config.json` and emits `blok-tokenizer-v2`. |
| The native C++ tokenizer could not reproduce Kimi's regex-sensitive numeric splitting. | The public Python path now performs exact Kimi tiktoken encoding and passes explicit token IDs through Rust to CUDA. The C++ tokenizer remains a fallback, not the parity path. |
| K and V rows were split by two bulk half-buffer copies. | A per-head split kernel now separates the checkpoint's interleaved KV rows correctly. |
| RoPE copied and rotated Q/K in one kernel, allowing cross-thread read/write races. | Copy and rotation are separate launches. |
| Prefill sampled the full language-model head for every input token. | Only the final prefill token runs the language-model head required for the first generated token. |
| Generation executed one unused final forward pass. | The final unused decode forward was removed. |
| Python accepted `max_time` but did not enforce it. | Native generation now has a subprocess timeout and raises a runtime error on expiry. |
| Metadata could become unavailable when the model filesystem was unmounted for raw uGDS access. | `BLOK_META_ROOT` is independent of `BLOK_MODEL_ROOT`; manifests, tokenizer data, maps, binaries, and environment files remain on the system filesystem. |
| Model materialization included checkpoint tensors not used by the text runtime. | Only `language_model.*` tensors are emitted into the runtime index. |
| CUDA used `--use_fast_math` despite a fidelity-first V0. | Fast math was removed. CUDA warnings are errors and ptxas optimization remains enabled. |
| Float activation paths did not emulate the checkpoint's BF16 boundaries. | Core matrix, normalization, residual, activation, router, and attention-output paths now round through BF16 at reference-relevant boundaries. |
| Selected MoE experts accumulated in selection order. | Expert computation is accumulated in ascending expert ID order while retaining the correct routing weight slot, improving deterministic behavior. |
| Model status accepted loose shard counts and aggregate file sizes. | Status now verifies the exact 64 shard filenames and the official index's total weight size. |
| Default model roots were derived from repository parent directories. | Defaults now use `~/.blok`; explicit environment roots remain supported. |

## Exact target-machine procedure

### 1. Establish safe storage boundaries

Do this before running `prepare`:

- Keep the repository, `BLOK_META_ROOT`, generated uGDS map, generated environment file, and binaries on the system filesystem.
- Put `BLOK_MODEL_ROOT` on the filesystem backed by the NVMe controller that will later be detached and bound to uGDS.
- Reserve `BLOK_KV_UGDS_BASE..BLOK_KV_UGDS_BASE+BLOK_KV_UGDS_BYTES` as dedicated raw space outside every mounted filesystem and outside all model extents.
- Never point KV scratch into filesystem “free space.” A filesystem may allocate that space later and corrupt either the filesystem or KV data.
- If the model files are inside a partition, set `BLOK_UGDS_PHYSICAL_OFFSET_ADD` to that partition's byte start on the whole device. FIEMAP offsets alone are filesystem/partition-relative.
- Back up anything valuable on the NVMe device before controller rebinding or raw writes.

The layout planner validates 4 KiB alignment, required-file FIEMAP coverage, unsupported extent flags, and overlap between mapped model extents and the declared KV scratch range. It cannot prove that an incorrectly declared raw KV range is unused by a filesystem; the operator must establish that boundary.

### 2. Initialize and bootstrap

From the repository root:

```bash
git submodule update --init --recursive
scripts/bootstrap_linux.sh
```

The uGDS submodule should resolve to `a7aa2046094bc290ca18530d09feda22c364306e` unless the repository itself is intentionally updated.

### 3. Export target paths and raw layout

The values below are examples. Replace every device/path/offset with values verified on the target:

```bash
export BLOK_HOME="$HOME/.blok"
export BLOK_MODEL_ROOT=/mnt/kimi-models
export BLOK_META_ROOT="$HOME/.blok/metadata"
export BLOK_UGDS_DEVICE=/dev/ugds_drv0
export BLOK_UGDS_MAP="$PWD/ugds-map.blok"
export BLOK_UGDS_ENV_OUTPUT="$PWD/ugds.env"
export BLOK_KV_UGDS_BASE=DECIMAL_BYTE_OFFSET_OF_RESERVED_RAW_REGION
export BLOK_KV_UGDS_BYTES=DECIMAL_SIZE_OF_RESERVED_RAW_REGION
export BLOK_UGDS_PHYSICAL_OFFSET_ADD=DECIMAL_PARTITION_START_OR_ZERO
```

Environment-variable meanings:

| Variable | Meaning |
| --- | --- |
| `BLOK_HOME` | Base for caches and default roots. |
| `BLOK_MODEL_ROOT` | Mounted checkpoint payload root; the script appends `moonshotai/Kimi-K2.6/source/hf/<revision>`. |
| `BLOK_META_ROOT` | Persistent sidecar root on a filesystem that remains mounted. |
| `BLOK_HF_TOKEN` | Optional Hugging Face token; passed only to the download child process. |
| `BLOK_HF_WORKERS` | Optional checkpoint download worker count; default 8. |
| `BLOK_UGDS_DEVICE` | uGDS character device used by the runtime. |
| `BLOK_UGDS_MAP` | Persistent output path for the FIEMAP-to-device map. |
| `BLOK_UGDS_ENV_OUTPUT` | Persistent shell exports loaded by the `run` phase. |
| `BLOK_UGDS_PHYSICAL_OFFSET_ADD` | Partition start in bytes when FIEMAP physical offsets must be translated to whole-device offsets. |
| `BLOK_KV_UGDS_BASE` | 4 KiB-aligned start of a dedicated raw KV scratch region. |
| `BLOK_KV_UGDS_BYTES` | Positive, 4 KiB-aligned size of that raw KV scratch region. |
| `BLOK_SMOKE_MAX_TIME` | Optional quality-smoke timeout in seconds; default 86400. |

### 4. Fetch the pinned checkpoint if it is not already present

```bash
scripts/model_fetch.py kimi-k2.6 status
scripts/model_fetch.py kimi-k2.6 fetch
scripts/model_fetch.py kimi-k2.6 status
```

A complete status must report 64 safetensors shards, `indexed_weight_bytes` equal to `595148192736`, and `complete: true`.

### 5. Prepare while the model filesystem is mounted

```bash
scripts/target_v0.sh prepare
```

This command must finish all of the following before the model filesystem is unmounted:

1. Create `manifest.blok`, `runtime-index.blok`, `layout-index.json`, and `tokenizer.blok` under the persistent metadata root.
2. Pass the exact tensor contract check.
3. Pass the exact tokenizer fixtures.
4. Prove model payload and metadata are on different filesystems.
5. Produce `ugds-map.blok` and `ugds.env` from FIEMAP.
6. Build `build/blok-kimi-exec`.
7. Build `target/release/blok` with the lockfile.
8. Build the uGDS kernel driver.

Do not move, rewrite, defragment, truncate, or redownload the shard files after the FIEMAP map is generated. Any change to their physical extents invalidates the map and requires rerunning `prepare`.

### 6. Unmount and bind the controller

Use the target's verified NVMe PCI address and the uGDS instructions under `sub_dir/uGDS/docs/installation.md` / `sub_dir/uGDS/scripts/env_switch.sh`:

1. Stop all processes using the model filesystem.
2. Unmount it cleanly.
3. Bind only the intended model NVMe controller to the uGDS-compatible driver.
4. Load/create the uGDS device as documented by the pinned submodule.
5. Confirm `/dev/ugds_drv0`, or the explicitly configured alternative, exists.

No PCI address is hard-coded in this repository because guessing it could detach the system disk.

### 7. Run the full correctness smoke

```bash
scripts/target_v0.sh run
```

The run phase sources `ugds.env`, points both native binaries at their release locations, uses the persistent manifest, checks the exact target hardware, rechecks the model contract, and invokes the public Python runtime. Success is a final line equivalent to:

```json
{"status": "ok", "text": "paris"}
```

Capture the complete output of `prepare` and `run` on the first target attempt. If the CUDA build or execution fails, those logs are the evidence needed for the next correction; do not bypass a failed contract, layout, or hardware check.

## What is not proven or implemented

These are explicit limits, not hidden completion claims:

1. The CUDA source has not been compiled by NVCC in this environment.
2. No forward pass has run here because the target NVIDIA/uGDS stack and 595 GB checkpoint are absent.
3. No target result has been compared layer-by-layer or logit-by-logit with the official reference implementation. Repository verification levels L3 and L5 remain unimplemented.
4. The exact tokenizer path is Python -> tiktoken -> Rust -> CUDA. Invoking the C++ executor directly with only `--prompt` can differ for regex-sensitive input; direct callers should supply `--prompt-tokens`.
5. KV state is currently expanded FP32 and stored on raw SSD. It costs 4,997,120 bytes per token across 61 layers: about 1.31 TB at 262,144 tokens and 4.997 TB at one million tokens. This V0 is therefore suitable only for a short correctness smoke on the 1 TB target device.
6. A compressed BF16 MLA latent cache would be about 70.3 GB for one million tokens, but that cache representation is not implemented.
7. Million-token input/output, concurrent prompts, concurrent models, multi-model scheduling, crash recovery, and 50-trillion-parameter addressing are not V0 features.
8. There is no measured throughput, time-to-first-token, power, or performance claim.
9. Architecture-specific inline PTX and low-precision tensor-core kernels were not added. Those should follow target compilation and parity, with measurements proving they improve the actual bottleneck.
10. The exact motherboard PCIe/IOMMU topology and model-NVMe PCI address are unknown to this development environment and must be verified on the target.
11. `end_goal_prompt.py` remains a future acceptance contract rather than a passing V0 test.

For scale context only, 50 trillion parameters require at least 25 TB at 4 bits/parameter, 12.5 TB at 2 bits/parameter, or 6.25 TB at 1 bit/parameter before metadata, cache, alignment, and redundancy. That goal necessarily requires a materially larger storage topology than the stated 1 TB target.
